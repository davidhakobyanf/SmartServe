# Серверные списки и фильтры

Клиентское меню и CRM запрашивают только нужную страницу. Поиск, фильтрация,
сортировка и подсчёт записей выполняются в PostgreSQL, до `LIMIT / OFFSET`.
Фронтенд отображает ответ и отправляет новые параметры при изменении фильтра.

## Маршруты

- Сотрудники: `GET /api/lists/products`, `categories`, `sauces`, `orders`, `users`, `roles`, `tables`.
  Требуется JWT и соответствующее разрешение; финансовые поля скрыты без `revenue.view`.
- Гости: `GET /api/guest-lists/products`, `categories`, `sauces`, `orders`.
  Требуется `x-session-token` открытого посещения. Заказы ограничены этой сессией;
  переданный в query чужой `sessionId` не меняет область доступа.
- Старые маршруты сохранены для совместимости. Новые экраны списков их не используют.

## Параметры

| Параметр | Значение |
| --- | --- |
| `page` | Страница, от 1 до 10000; по умолчанию 1 |
| `pageSize` | Размер страницы, от 1 до 100; по умолчанию 24 |
| `search` | До 200 символов; поиск по всем переводам, без учёта регистра для en/ru/am |
| `categoryId`, `sauceId` | UUID фильтров товаров; применяются вместе с поиском |
| `id` | Одна запись товара/категории/соуса/роли, например выбранная опция за пределами первой страницы |
| `isActive` | `true` / `false` для товаров, категорий, соусов и ролей |
| `sort` | Товары: `default`, `newest`, `oldest`, `price-asc`, `price-desc`, `name` |
| `status` | Заказы: `all`, `active`, `history`, `placed`, `preparing`, `ready`, `completed`, `cancelled`; сотрудники: `all`, `pending`, `active`, `rejected`, `disabled`; столы: `all`, `open`, `available`, `inactive` |

`Accept-Language: am`, `ru` или `en` определяет отображаемые названия и сортировку
по имени. `%` и `_` в поиске считаются обычными символами, а не SQL-шаблонами.
У товаров недоступные позиции гостевого меню идут после доступных; неактивные
категории и соусы гостям не выдаются. Категории/соусы/роли в select тоже загружаются
страницами с серверным поиском.

Пример: `/api/lists/products?page=2&pageSize=12&search=soup&sort=price-asc`.

Ответ: `{ items, total, page, pageSize, totalPages, unfilteredTotal }`.
`total` — количество после фильтров, `unfilteredTotal` — размер доступного набора
до поискового фильтра. При пустом результате `items=[]`, `page=1`, `totalPages=0`.
Если последнюю страницу удалили, сервер возвращает последнюю существующую.
Заказы, сотрудники и столы дополнительно возвращают `stats`: статистика относится
ко всему доступному набору, а не только текущей странице. Заказы также возвращают
`filterCounts` для вкладок статусов.

## Обновления в реальном времени

- `orders:invalidated` в namespace `orders` сообщает сотрудникам об изменённом
  заказе; финансовая сумма есть только в комнате `revenue`.
- `order:changed` в namespace `sessions` отправляется только комнате посещения
  клиента. Статус `ready` вызывает уведомление даже для заказа вне текущей страницы.
- `menu:updated` обновляет текущую страницу меню после изменения товара,
  категории или соуса. Переподключение сокета также запускает повторный запрос.

## Запуск и проверка

Обновлять API и frontend нужно вместе. Применить миграции штатным способом
проекта (при `DB_MIGRATIONS_RUN=true` — на запуске API).
`AddListingIndexes1788930000000` добавляет пять индексов для страниц товаров,
заказов и сотрудников; таблицы и данные не удаляются. B-tree индексы не ускоряют
произвольный поиск подстроки: для очень большого каталога потребуется отдельная
оптимизация полнотекстового/триграммного поиска после измерений.

`npm test -- --runInBand` в `api` запускает обычные проверки. Для интеграционных
проверок списков на **локальной тестовой** PostgreSQL задать `LISTING_TEST_DB_HOST`,
`LISTING_TEST_DB_PORT`, `LISTING_TEST_DB_USER`, при необходимости
`LISTING_TEST_DB_PASSWORD` и `LISTING_TEST_DB_NAME`. Тест создаёт отдельную случайную
схему `listing_test_*`, заполняет её и удаляет только собственную схему после проверки.
Без этих настроек интеграционный набор пропускается.
