# Разбор рефакторинга backend SmartServe

Изменения оставлены локально, без commit и push. Этот файл — маршрут для
совместного разбора: можно проходить по одному пункту за разговор.

## Что изменилось

У сервера осталась feature-first структура: пользователи в `users/`, продукты
в `products/`, заказы в `orders/`. Внутри этих разделов обязанности стали явнее.

| Компонент | За что отвечает | Что вынесено из него |
| --- | --- | --- |
| `UsersService` | Общая точка входа в операции с пользователями, фасад | Вход/регистрация, управление сотрудниками, запросы к БД |
| `UserAuthenticationService` | Регистрация, проверка пароля и статуса, выдача JWT | Получил эти сценарии из `UsersService` |
| `StaffManagementService` | Одобрение заявок, смена статуса/роли/личных прав, защита владельца | Получил управление сотрудниками из `UsersService` |
| `UsersRepository` | Поиск пользователя и аватара, список сотрудников, сохранение профиля | Получил повторно используемые запросы из `UsersService` |
| `getEffectivePermissions` | Вычисление итоговых прав из роли, allow и deny | Обычная функция, не требует NestJS и БД |
| `ProductsService` | Последовательность создания, изменения и удаления продукта | Запросы, работа со связями соусов и чтение изображений |
| `ProductsRepository` | Запросы с нужными relations/сортировкой, запись продукта, проверки ссылок | Изолирует работу с TypeORM |
| `ProductSaucesService` | Проверка ID соусов и замена связей с продуктом | Изолирует правила работы со связями |
| `ProductImagesService` | Чтение изображения продукта и обновление его изображения/метаданных | Изолирует особенности изображений продуктов |
| `StaffSocketAuthService` | JWT, статус сотрудника, активность роли и permission для WebSocket | Общая проверка для orders и waiter |
| Функции `*-response.ts` | Сборка публичного ответа, перевод полей, сокрытие данных по правам | Убрали сборку JSON из контроллеров |

Например, `UsersService` сократился с 383 до 75 строк. Код его сценариев теперь
находится в небольших именованных компонентах. `ProductsService` сократился
с 307 примерно до 160 строк. Общая длина проекта выросла из-за явных границ,
документации и тестов; цель — понятная ответственность каждого файла.

## 1. Сначала проследим один запрос: вход в систему

Открой [auth.controller.ts](../src/auth/auth.controller.ts).

`@Controller("api")` задаёт общий префикс. `@Post(["user/login", "auth/login"])`
означает, что два прежних адреса вызывают один метод `login`. `@Body()` передаёт
проверенные данные запроса. Контроллер вызывает `usersService.login(dto)`.

Дальше открой [users.service.ts](../src/users/users.service.ts). Его `login`
передаёт работу в `authentication.login(dto)`. Этот класс называется фасадом:
другие части проекта продолжают пользоваться привычной точкой входа.

Теперь открой [user-authentication.service.ts](../src/users/user-authentication.service.ts).
Здесь находится сам сценарий: найти пользователя вместе с ролью, сравнить пароль,
проверить статус и роль, подписать JWT с `sub = user.id`, сохранить `lastLoginAt`
и вернуть прежние четыре поля ответа.

На первом разборе достаточно понять три вопроса: кто принимает HTTP-запрос,
кто решает, можно ли войти, и кто обращается к базе. Начинать с всех файлов сразу
не требуется.

## 2. Как классы получают друг друга

Открой [users.module.ts](../src/users/users.module.ts).

`providers` регистрирует классы, экземпляры которых создаёт NestJS. Если
`UsersService` указывает `UserAuthenticationService` в конструкторе, NestJS
передаёт ему зарегистрированный экземпляр. Это называется внедрением зависимостей.
`exports` делает нужные компоненты доступными другим модулям.

`TypeOrmModule.forFeature([User, Role])` предоставляет репозитории этих сущностей.
`@InjectRepository(User)` в конструкторе запрашивает репозиторий пользователя.
Простые операции используют готовый `Repository` TypeORM; дополнительные классы
запросов введены там, где нужно дать понятные имена нескольким связанным запросам.

В тестах вместо реальной базы передаются объекты с контролируемыми ответами.
Поэтому можно проверить сценарий, включая ошибку сохранения, без подключения
к рабочей базе.

## 3. Сотрудники и права доступа

В [staff-management.service.ts](../src/users/staff-management.service.ts) разберём
одобрение заявки, затем смену роли и защиту последнего активного владельца.
Последовательность проверок и тексты ошибок сохранены.

В [effective-permissions.ts](../src/common/auth/effective-permissions.ts) находится
правило: права роли плюс личные разрешения, затем удаление запрещённых прав.
Для владельца по-прежнему возвращается полный список permissions.
Эту функцию можно проверить обычным входным объектом без запуска сервера.

## 4. Как формируется ответ frontend

Начнём с [user-response.ts](../src/users/user-response.ts), затем посмотрим
[profile-response.ts](../src/profile/profile-response.ts) и
[role-response.ts](../src/roles/role-response.ts).

Сущность из базы и JSON для браузера — разные вещи. Например, пароль нужен для
сравнения при входе, но его нет в ответах профиля и списка сотрудников.
Именованные функции ответа явно показывают, какие поля получит браузер.

[table-response.ts](../src/tables/table-response.ts) и
[session-response.ts](../src/sessions/session-response.ts) сохраняют различие
между гостевым и служебным ответами. Без `tables.qr.manage` поле `publicToken`
не попадает в JSON. В заказах закрытые денежные поля остаются `null`.

## 5. Создание и изменение продукта

В [products.service.ts](../src/products/products.service.ts) проследим метод
`create`. Он координирует проверку категории, проверку соусов, обработку данных,
сохранение продукта, запись связей и загрузку подробного результата.

В [products.repository.ts](../src/products/products.repository.ts) находятся
конкретные запросы. `relations` указывает, какие связанные сущности загрузить;
`order` задаёт сортировку. Эти параметры перенесены без изменения.

[product-sauces.service.ts](../src/products/product-sauces.service.ts) занимается
таблицей связей. [product-images.service.ts](../src/products/product-images.service.ts)
загружает байты изображения через `addSelect`, поскольку у поля `imageData`
в сущности задано `select: false`.

## 6. Общие функции: переводы, изображения, соусы

[localized-text.ts](../src/common/i18n/localized-text.ts) теперь содержит
`updatedLocalizedText`: переданный объект переводов заменяет существующие
переводы, а старое строковое поле обновляет английский перевод. Правило nullable
имени стола отличается, поэтому оно осталось в `TablesService`.

[image-upload.util.ts](../src/common/utils/image-upload.util.ts) содержит
декодирование и `imageReplacement`. Для категории и соуса удаление изображения
имеет приоритет над загрузкой. У продукта сохранено отдельное поведение:
он также разрешает обновить метаданные без новых байтов. Аватар сохраняет свою
более строгую проверку MIME-типа в `ProfileService`.

[image-response.ts](../src/common/http/image-response.ts) собирает данные
изображения и отправляет прежние заголовки и байты в HTTP-ответе.

[sauce-selection.ts](../src/sauces/sauce-selection.ts) нормализует ID, сравнивает
выбор соусов и строит снимки их названий и цен. В ней нет запросов к БД.

## 7. Заказ, транзакция и события

[order-calculation.ts](../src/orders/order-calculation.ts) считает стоимость
строки, общий итог и создаёт снимок позиции. Например, `(0.1 + 0.2) × 3`
по прежнему алгоритму округляется до `0.9`.

[orders.service.ts](../src/orders/orders.service.ts) сохраняет транзакцию:
блокировка сессии, чтение корзины, создание заказа, очистка корзины. Только после
успешного завершения транзакции отправляются события изменения корзины и заказов.
Тест отдельно имитирует ошибку commit и проверяет отсутствие событий.

Снимок хранит название, описание и цену на момент заказа. Изменение текущего меню
не должно менять уже сохранённую историю заказа.

## 8. Обновления без перезагрузки страницы

[staff-socket-auth.service.ts](../src/users/staff-socket-auth.service.ts) проверяет
сотрудника для двух каналов. Gateway передаёт нужное permission и прежнее сообщение
для неактивного пользователя. Поэтому общая проверка сохраняет различия ошибок
между `orders` и `waiter`.

После успешной проверки [OrdersGateway](../src/orders/orders.gateway.ts) выбирает
комнату `orders` или `revenue`. [WaiterGateway](../src/waiter/waiter.gateway.ts)
добавляет сотрудника в `admin`. Названия каналов, событий, комнат, handshake-поля
и acknowledgement-ответы сохранены.

## 9. Как проверять изменения

Из каталога `api/`: `npm test` и `npm run build`.
Из каталога `app/`: `npm run lint` и `npm run build`.

Исходные 27 тестов сохранены. У существующего теста `ProductsService` изменена
только сборка зависимостей; проверки поведения остались прежними.
Всего после рефакторинга: 19 suites, 90 tests, 50 snapshots — проходят.
Обе сборки и frontend lint проходят.

`contracts/http.contract.spec.ts` поднимает временный сервер на `127.0.0.1` и
проверяет реальные маршруты NestJS, guards, DTO-validation, сериализацию JSON
и заголовки изображений. Сервисы persistence заменены фиктивными данными.
На рабочую базу эти тесты не ходят. В ограниченной среде запуск локального
HTTP-сервера может требовать разрешения.

`contracts/modules.contract.spec.ts` собирает настоящий `AppModule` с подменой
подключения к БД и проверяет, что NestJS разрешает новые зависимости.
`websocket.contract.spec.ts` проверяет обработчики gateway и отправку сообщений
через фиктивные sockets; это не браузерный end-to-end тест.

Полный прогон с реальным PostgreSQL и браузером в этой работе не выполнялся.
Проверки с mocks не доказывают поведение базы при конкурентных запросах.

50 snapshots записаны на исходной реализации до рефакторинга. Не обновляй их
просто ради зелёных тестов: сначала нужно понять причину расхождения.
Тестовые fixtures исключены из production-сборки через `tsconfig.build.json`.

## Что сохранено и что оставлено отдельной задачей

Frontend, entities, migrations, DTO, HTTP guards, package.json/lockfile и
конфигурация запуска не изменены. Изменены только файлы внутри `api/`.
Список HTTP-контрактов: [contracts.md](contracts.md).

Конфигурацию TypeORM не объединял: у runtime и CLI разные пути к миграциям,
преобразование порта и настройка автоматического запуска миграций. Этот небольшой
участок оставлен как есть, чтобы не менять поведение запуска и deployment.

Обнаруженные особенности исходной реализации, сохранённые в этом рефакторинге:

1. Изменение продукта сохраняет его до проверки нового списка соусов; сохранение
   продукта и замена связей не образуют одну транзакцию. При ошибке соусов возможно
   частичное обновление. Это поведение отражено отдельным тестом; исправление
   требует отдельной задачи с изменением транзакционных границ.
2. Проверка числа активных владельцев и изменение роли/статуса не защищены общей
   блокировкой. Одновременные запросы требуют отдельного анализа конкуренции.
3. В `orderResponse` без revenue.view скрываются total, unitPrice и lineTotal,
   но ценовые snapshots соусов передаются как раньше. Расширение сокрытия —
   отдельное изменение API/прав доступа.
4. HTTP и WebSocket имеют разные fallback CORS origins. Значения окружения,
   JWT defaults и эта особенность не менялись.

Старое архитектурное описание в корневом `AGENTS.md` не соответствует текущим
сущностям, guards и миграциям. Для разбора используем актуальный исходный код.
